# 修复前端对话失败并补充后端集成测试计划

## 1. Summary
- 目标：解决前端聊天窗口出现“抱歉，生成回答时出现错误，请稍后再试”的问题，并补齐后端 API 自动化集成测试。
- 成功标准：
  - 对话接口在常见异常场景下不再返回泛化报错文案，且能给出稳定可用回复（按用户选择“对话必须成功”）。
  - 新增后端 API 集成测试，覆盖成功路径与失败路径，测试可本地一键执行。
  - 前端在后端返回业务失败时展示服务端可诊断信息，而不是统一“网络错误”。

## 2. Current State Analysis
- 前端调用链（已确认）：
  - 文件：`rag_front/src/components/RagChat.vue`
  - `sendMessage()` 调用 `POST ${API_BASE}/query`，请求体包含 `question` 与 `collection_name`。
  - `catch` 分支固定展示“网络错误或服务不可用”，会掩盖后端业务错误信息。
- 后端调用链（已确认）：
  - 文件：`api_integration.py`
  - `POST /api/vector/query` 始终将 `vector_retriever.answer_question()` 的结果封装为 `success: true` 返回。
  - 文件：`vector_retriever.py`
  - `_generate_answer_with_llm()` 捕获所有异常后返回固定文案“抱歉，生成回答时出现错误，请稍后再试。”，导致前端看到该文案但无法定位原因。
- 环境与配置（已确认）：
  - `.env` 已配置 `LLM_BASE_URL=https://api.minimax.chat/v1`、`LLM_MODEL=MiniMaxAI/MiniMax-M2.5`。
  - 当前项目没有现成测试框架（无 pytest/vitest 配置），仅有手工脚本 `test/milvus_*.py`。
- 已知风险（从代码与日志行为推断）：
  - LLM 调用异常被吞并为静态文案，无法区分配置错误、网络异常、模型不可用。
  - API 语义与真实状态不一致（异常也返回 `success: true`），影响前端分支处理与自动化断言。

## 3. Proposed Changes

### A. 后端：重构问答错误语义与降级策略
- 文件：`vector_retriever.py`
- 变更内容：
  - 新增 LLM 调用结果结构（例如 `answer + error_code + error_message + used_fallback`）。
  - `_generate_answer_with_llm()` 失败时不再只返回固定文案；改为：
    - 记录可诊断错误（日志中保留原始异常）。
    - 按“对话必须成功”策略返回降级回答（如“知识库未命中时的通用回答模板”或“基于检索上下文的摘要回答”）。
  - `answer_question()` 透传降级标记和错误元信息供 API 层使用。
- Why：
  - 避免前端收到无法定位的静态失败文案。
  - 保证对话可用性优先，同时保留可观测性。
- How：
  - 以“成功回复与失败诊断并存”的数据结构替代纯字符串返回。
  - 对异常分级（认证/网络/模型调用/未知错误）映射统一错误码。

### B. 后端 API：返回真实业务状态与可诊断字段
- 文件：`api_integration.py`
- 变更内容：
  - 调整 `/api/vector/query` 返回协议：
    - 正常：`success: true`，包含 `answer`、`sources`、`confidence` 等。
    - 降级成功：`success: true`，增加 `degraded: true` 与 `warning` 字段。
    - 彻底失败：`success: false`，返回 `message`（可诊断但不泄漏敏感信息）。
  - 保持现有字段兼容，避免前端大改。
- Why：
  - 让前端可以按业务语义展示提示，避免把业务失败误判成网络失败。
- How：
  - 在封装响应前根据 retriever 返回的状态进行分支。

### C. 前端：改进错误展示与降级提示
- 文件：`rag_front/src/components/RagChat.vue`
- 变更内容：
  - 在 `catch` 分支优先显示 `error.response?.data?.message`，其次再显示网络错误文案。
  - 在成功但降级时（`degraded: true`）显示轻提示，不影响主回答渲染。
- Why：
  - 用户能看到可执行的错误信息，减少“黑盒报错”。
- How：
  - 只调整 `sendMessage()` 内错误处理与消息渲染数据结构，不改 UI 主布局。

### D. 自动化测试：新增后端 API 集成测试
- 新增文件：`tests/test_query_api.py`
- 变更内容：
  - 使用 Python 内置 `unittest` + Flask `test_client`（避免新增测试框架依赖）。
  - 覆盖用例：
    - `query` 参数缺失返回 400 + 明确 message。
    - 模拟 LLM 异常时接口仍可返回降级成功（`success: true` 且 `degraded: true`）。
    - 模拟不可恢复错误时返回 `success: false` 且 message 可诊断。
  - 通过 monkeypatch/stub 替代真实 Milvus 与真实 LLM 调用，保证测试稳定离线运行。
- Why：
  - 锁定回归风险，确保“对话必须成功”的策略可持续。
- How：
  - 在测试中 patch `api_integration.vector_retriever` 或其方法返回受控结果。

### E. 测试执行入口与文档
- 文件：`README.md`（若已有后端运行说明则追加一节）
- 变更内容：
  - 增加“后端 API 集成测试”执行说明：`python -m unittest discover -s tests -v`。
  - 标注测试不依赖外部 Milvus/LLM 的前提。
- Why：
  - 降低后续维护与复现成本。
- How：
  - 仅新增简短说明段落，不改现有主结构。

## 4. Assumptions & Decisions
- 已确认决策：
  - 修复目标选择“对话必须成功”。
  - 自动化测试范围选择“后端 API 集成测试”。
- 实施假设：
  - 当前前端与后端通过 `VITE_API_BASE` 直连，接口协议可小幅扩展字段。
  - 允许在 LLM 故障时返回降级回答（而非阻断式失败）。
- 兼容性策略：
  - 保留 `answer/sources/confidence` 原有字段，新增字段以可选方式扩展，降低前端破坏性。

## 5. Verification Steps
- 静态验证：
  - 运行编辑文件诊断，确保无语法错误。
- 自动化测试：
  - 执行 `python -m unittest discover -s tests -v`，确认新增用例全部通过。
- 接口验证（本地）：
  - 调用 `/api/vector/query` 分别覆盖正常、降级、失败三类响应。
  - 检查响应 JSON 的 `success/degraded/message/answer` 语义符合预期。
- 前端联调验证：
  - 在聊天窗口发送问题，确认不再出现固定“抱歉，生成回答时出现错误，请稍后再试”作为唯一反馈。
  - 在后端返回业务失败时，前端可展示服务端 message。
